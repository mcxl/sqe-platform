Final Architecture And Service Contract

  • ClientReleaseService owns draft creation, validation, publication, withdrawal, current-release selection, history, version allocation, and creation/withdrawal audit coordination
  • ClientReleaseStorage owns parameterised release SQL and always uses the caller-supplied SQLite connection
  • ClientReleaseProjection owns pure, transport-neutral response projection from caller-supplied immutable release snapshots; it performs no SQL, connection work, authentication, G0 evaluation, HTML rendering, or writes
  • Web routes contain no release SQL and retain HTTP, authentication, G0, error translation, one connection, service reads, and HTML rendering
  • begin_release_write() acquires caller-owned BEGIN IMMEDIATE before allocation reads; the caller retains commit and rollback ownership
  • The completed projection is ready for a future read-only mobile adapter; no mobile application was added

Database Controls And Migration Evidence

  • All 18 release-related triggers retained after classification; none was redundant without weakening direct-SQL, migration, lineage, isolation, immutability, uniqueness, or publication-audit protection
  • The client_release_packages_auto_publish_event trigger remains the owner of RELEASE_PUBLISHED audit creation
  • WorkbenchStore remains the migration and trigger-installation owner
  • Fresh, Phase 6A, Phase 6B1, predecessor-trigger, and repeated-reopen states retain the exact trigger inventory with no stale _old references
  • Complete immutable audit snapshots and legacy nullable-ID release history remain preserved across upgrades and reopens
  • API and HTML behaviour remains unchanged; G0, client read-only access, and engagement isolation remain active
  • All 18 release-related triggers remain present, and no-mutation snapshots confirm client reads leave packages, entries, sources, and audit rows unchanged

Lessons And Remaining Boundary

  • Acquire SQLite write intent before version-allocation reads; upgrading an already-read deferred transaction is not a safe concurrency contract.
  • Pass one active connection through every service and storage call; opening a second connection inside a transaction risks lock failures.
  • Compare complete immutable audit rows, not counts alone, when proving migration and reopen stability.
  • Direct SQL can still perform a minimal PUBLISHED → WITHDRAWN transition without complete withdrawal metadata or a withdrawal audit event. The service-owned workflow guarantees completeness; adding database enforcement would be a separately scoped behaviour change.
